# 为 Nyarugram 实现聊天端到端加密与账号级四位 PIN

请完成以下功能的协议设计、客户端和后端实现、相关回归及 APK 交付，不只提供界面原型或加密方案。客户端位于 `W:\Work\Botgram`，后端位于同级 `../Botgram.Backend`。开始前阅读各仓库的 `AGENTS.md`，以及客户端 `Botgram.Android.md`、`Botgram.GID.md`、`Botgram.Chinese.md`；涉及服务运行再阅读后端 `DEPLOYMENT.md`。核对当前源码与工作区，保留已有用户修改。

项目要求用户自行部署后端、数据库、TLS 和必要配套服务，不添加公共服务器地址、默认公共连接目标或第三方托管密钥服务。本任务不自动授权升级、重启正式服务或修改正式数据。

## 一、产品目标与范围

在现有一对一聊天中增加真正的端到端加密，保留原 `ProfileActivity`、`ChatActivity`、会话列表、消息气泡和设置导航，不另建独立 Activity 或替代聊天应用。

首期支持普通用户之间的一对一文字消息；联系人和非联系人均可使用。自己、机器人、群组、频道及已删除账号不提供可成功启用的入口。附件、语音、通话、群聊、多设备同步和换机恢复不属于首期支持范围，界面不得暗示这些内容已受本功能保护。已有通话与普通聊天功能不得被无关修改破坏。

同一账号的全部加密聊天共用一个四位数字 PIN。不同账号独立，双方各自设置自己的 PIN，无需相同，也不相互传递。允许前导零。PIN 无法找回，不提供服务端恢复、密码找回或管理员解密能力。

## 二、个人主页入口与启用流程

- 在普通用户个人主页增加一行操作，位置参考非联系人个人主页的“添加为联系人”按钮所在区域。非联系人仍保留原添加按钮，已是联系人时加密入口也必须显示，不受 `addToContactsRow` 的显示条件限制。
- 左侧标题为“端到端加密”，右侧显示“关闭”或“启用”。使用原生列表组件分别布局，不能通过连续空格拼接标题和状态。
- 首次点击关闭状态：进入 PIN 设置页，输入四位数字，再次输入确认；确认一致后建立本机密钥保护，再发起当前聊天的加密握手。
- 当前账号已配置 PIN：进入同一页面验证已有 PIN，通过后为当前聊天建立加密会话，不要求为每个聊天重新设置 PIN。
- 设置时清楚提示：“此账号的所有端到端加密聊天共用此 PIN。PIN 无法找回；丢失后将无法解锁本机加密聊天。”提供明确确认动作。
- PIN 设置成功不等于当前聊天已经启用。双方设备完成密钥协商、身份处理及激活确认后才显示“启用”。协商中显示“等待对方”或相应进度，错误可重试，取消和重复请求必须幂等。
- 对方离线时保留可恢复的待处理状态；对方客户端不支持时明确提示，不能伪造成功，不能把消息自动按普通明文发送。
- 对方收到邀请时提供明确的原生确认流程；尚未设置账号 PIN 的接收方先完成同样的 PIN 设置。双方确认的状态必须一致，不能仅由发起方的本地开关决定聊天安全状态。
- 已启用入口点击后验证 PIN，再显示管理操作，包括查看会话安全码及关闭。关闭需确认，双方确认消息模式分界后才允许后续普通消息；失败、超时和离线期间保持安全状态，禁止单方面静默降级。

## 三、复用密码锁页面，但隔离密码与状态

先检查当前 `PasscodeActivity`、`PrivacySettingsActivity` 及 `SharedConfig` 的实际实现。密码锁页面现有逻辑会读写全局应用密码锁，不能直接复用其保存操作。

- 为 `PasscodeActivity` 提取可复用的输入、确认与验证能力，或增加独立的聊天加密用途模式。复用原布局、数字键盘、主题、动画、错误反馈和无障碍行为。
- 聊天 PIN 固定为四位数字，不显示切换长密码或其他位数的入口。
- 聊天 PIN 与应用密码锁分别存储、分别验证，修改、关闭或重置任意一项不得影响另一项；应用原自动锁定行为保持正确。
- 账号隔离至少包含规范服务器身份、账号稳定 UUID 和本机设备身份，不能仅以账号槽位、用户名或 Gram ID 作为永久主键。
- 更改 PIN 必须验证旧 PIN，只重新封装本机密钥库，不更换账号 UUID、TL ID、聊天关联或对端已验证身份。
- 忘记 PIN 不提供找回。允许在明确确认不可逆后销毁本机加密密钥并重新建立会话；不能让普通账号登录密码、恢复码或后端管理员绕过 PIN 解密旧消息。说明该操作不删除对方持有的消息，也不保证清除备份和闪存中的历史副本。
- 明确锁定策略：首期默认应用退到后台、冷启动或切换账号后重新锁定；内存密钥在锁定、退出和会话替换时尽快清理。后台可接收并保存密文，不能为了后台解密把明文 PIN 或解锁密钥落盘。
- 对失败验证实施持久化的退避/限速，考虑重启绕过和并发尝试，不采取未告知用户的自动毁钥策略。

## 四、隐私和安全中的管理列表

- 在“设置 → 隐私和安全”增加“对聊天进行端到端加密”，放在密码锁附近，使用原生设置行和导航。
- 点击打开基于 Telegram `BaseFragment` / `UniversalFragment` 和列表组件的管理页面。
- 列出当前账号的全部已启用加密聊天；待协商会话可单独显示状态，不冒充已启用。显示头像、名称和状态，点击验证 PIN 后进入原聊天页。
- 没有已启用或待处理会话时，居中显示锁和钥匙图标，以及精确文案“暂无端到端加密聊天”。图标优先复用现有图形资源与主题颜色。
- 页面提供“更改 PIN”，有密钥库时先验证旧 PIN；无 PIN 时不展示无法执行的更改操作。
- 列表与资料页、聊天页状态同步，正确处理取消、关闭、失败回滚、重启恢复、删除联系人、屏蔽、账号切换和页面销毁。移除联系人不应误销毁加密历史，屏蔽关系优先于加密邀请和发送权限。

## 五、密码学与信任模型

四位 PIN 只有一万种组合，不能作为消息密钥、共享口令或唯一的离线密钥保护。PIN 的用途是解锁本机密钥库，消息加密必须使用密码学安全随机生成的高强度密钥。

- 优先选择经过审查、可维护、许可兼容且适配当前 Android API 范围的成熟端到端加密协议和实现，具备异步会话建立、身份认证、前向保密、密钥演进及重放防护。评估依赖来源、固定版本、校验值、许可证、原生 ABI 和构建成本，不自行拼装未经评审的密码协议。
- 结合 Android Keystore 中不可导出的设备密钥、带随机盐的适当 PIN 派生及认证加密保护本机密钥库；明确设备绑定及卸载、清数据、Keystore 失效后的后果。记录实际安全保证，不能声称四位 PIN 能抵抗设备完全失陷后的全部攻击。
- 后端只处理公钥、预密钥、必要的会话状态、密文与投递元数据，不持有 PIN、可恢复的 PIN 校验材料、私钥、消息明文或能替代用户解锁的主密钥。
- 会话绑定双方稳定账号身份、服务器身份、设备和协议版本。提供双方可核对的安全码/指纹，说明首次信任的限制；身份密钥变化时暂停受影响的加密发送并明确提醒重新确认，不能静默信任替换公钥。
- 设计单次预密钥消费、并发发起、离线重试、重放、乱序、重复投递、消息密钥删除及设备撤销。限制跳过密钥和待处理队列的大小，防止资源耗尽。
- 即使开启 E2EE，后端仍能看到收发双方、时间和消息大小等投递元数据；不得宣称隐藏全部通信关系。HTTPS 与 Bearer 鉴权继续保留。
- 只用模拟加解密、固定密钥、Base64、可逆混淆、TLS 或服务端加密，均不能作为实现完成。

## 六、现有协议、消息流和本地存储

先追踪实际的发送、重发、编辑、历史分页、差分、事件唤醒、缓存、通知和原生 TL 控制器路径，定义清楚拦截点后实现。

- 使用独立、版本化的 typed Protobuf 密文信封及握手操作，保留现有协议字段编号和兼容规则；不要把密文伪装成普通消息文本，避免旧客户端展示乱码或服务端明文索引处理。
- 服务端按会话版本与加密分界执行状态检查，拒绝应加密阶段的普通明文发送。旧客户端和版本不支持时明确拒绝，不提供自动 JSON 或明文回退。
- 密文信封认证必要的会话、发送设备、密钥轮次及协议上下文。协调发送幂等标识、密钥演进及本地事务，崩溃重试不得造成 nonce/密钥重用，重复消息不得重复推进状态。
- 后端存储、日志、错误、审计、全文搜索和备份中不得出现加密消息正文。不要把现有服务端富文本解析、摘要、搜索或机器人处理直接套用到密文。
- 客户端只在解锁后解密供原聊天 UI 展示；本地数据库、发送队列、草稿、搜索索引、缓存、引用摘要和日志不得再保存加密区间的明文。不能只在网络 Mapper 层加密，而任由原 MessagesStorage 将解密内容持久化。
- 对富文本、回复摘要、转发、编辑、收藏、导出、复制与分享逐项给出首期支持矩阵。未实现的跨会话操作在发出请求或产生明文副本前明确阻止，不能悄悄绕过加密；屏蔽加密聊天的远程链接预览。
- 原聊天页显示可靠的锁标识与启用分界。只有分界之后的新消息受保护，不能声称已有服务器明文历史被追溯加密或删除。
- 锁定时不显示加密正文、引用或搜索摘要，消息通知只显示“收到一条加密消息”；未锁定时首期也不在系统通知中显示正文。检查通知更新、气泡、分享预览和最近任务缩略图等泄漏路径。
- 重装、换机或设备密钥失效后，首期不恢复旧加密历史；重新建立会话时清楚标记身份变化。不能以服务器能下发密文为依据承诺可解密。
- 多账号、退出重登、同一槽位替换会话时，隔离请求、数据库、密钥及迟到回调，不能落回 Telegram 原生网络或其他账号的密钥库。

## 七、实现与验证步骤

1. 先提交仓库内可审阅的设计说明，包含威胁模型、成熟协议选型、PIN 与 Keystore 的关系、设备与账号身份、启停状态机、消息分界、存储路径和首期支持矩阵。随后按方案实现，不将设计文档当作最终交付。
2. 实现独立 PIN 模式、原资料页入口、原隐私页入口和管理列表，补齐英文及简体中文。中文同时维护 `Tools/Import-BotgramChinese.ps1` 字典，再运行脚本生成资源。
3. 实现协议、后端密文投递与状态校验、客户端会话密钥管理、真实消息流及本地加密存储。后端数据库变更提供兼容迁移与回滚边界，不能重建账号或清库解决问题。
4. 在独立数据目录和隔离测试账号中完成回归，不访问或写入正式用户数据。使用现有已下载环境；所有新依赖、工具和缓存放 `D:\BotgramBuild`，固定版本和校验值。
5. 全部源码完成后编译交付变体，再验证最终产物。运行后端指引要求的相关回归、Protobuf 映射和适用的真实 TL 二进制验证，不以 UI 冒烟代替密码学和消息流验证。

至少覆盖以下验收：

- 联系人和非联系人入口、已有 PIN 复用、二次确认、前导零、修改 PIN、应用密码锁隔离、多账号隔离、空列表和锁钥图标。
- 两个真实客户端身份完整握手、双方安全码一致、文本收发与历史重载；双方离线、重复点击、同时发起和取消恢复。
- 错误 PIN、持久化退避、冷启动与后台锁定、忘记后毁钥、Keystore 失效；错误解锁不能修改会话或密钥状态。
- 消息篡改、身份替换、错误接收者、重放、乱序、重复、跳过密钥上限、跨账号/设备/会话替换、无效协议版本及未认证调用。
- 发送与密钥状态持久化之间崩溃、重试幂等、开启/关闭与发送并发、旧客户端发送、断线重连和差分重放；不得产生静默明文降级。
- 在隔离样本的服务端数据库、客户端持久化文件、日志、发送队列、草稿与通知中检查已知测试明文的泄漏，并检查私钥/PIN 不出现在网络和后端。不得将敏感测试材料打包到 APK 或交付日志中。
- 已有明文聊天、联系人、资料页、应用密码锁、账号切换和普通通话的相关回归；未支持的加密操作明确拒绝。
