# 为 Nyarugram 联系人实现“特别关心”与分级来电通知

请直接完成实现、相关验证和 APK 交付，不只给出方案。客户端位于 `W:\Work\Botgram`，后端位于 `W:\Work\Botgram.Backend`。开始前阅读各仓库 `AGENTS.md`，以及 `Botgram.Android.md`、`Botgram.GID.md`、`Botgram.Chinese.md`；涉及服务运行再阅读后端部署说明。以当前源码为准，保留已有修改。

## 产品目标

为联系人增加“特别关心”。设置入口、取消方式、确认弹窗和操作成功后的反馈，参考当前原 Telegram 页面中的“屏蔽用户 / 取消屏蔽”功能；收到特别关心联系人消息后的提醒体验参考 QQ 的特别关心。继续使用原资料页、聊天页、联系人和通知体系，不另建 Activity 或替代聊天界面。

把当前所有来电默认使用的 4 级通知改为特别关心联系人专属：

| 来电来源 | Android 8+ 新频道默认重要性 | 后台自动全屏通话入口 |
| --- | --- | --- |
| 当前账号的特别关心联系人，一对一语音或视频来电 | `IMPORTANCE_HIGH`（4） | 使用原通话页的 full-screen intent，满足系统条件时后台也可全屏展示 |
| 普通联系人、非联系人或身份尚未确认的来电 | `IMPORTANCE_DEFAULT`（3） | 不设置 full-screen intent，也不通过其他后台启动路径自动铺满屏幕；点击通知、接听后正常进入原通话页 |

4 和 3 是 Android NotificationChannel 的重要性数值，不是锁屏可见性，也不等于旧版 NotificationCompat 的 priority 数值。Android 系统对全屏权限、锁屏、前台状态和用户通知设置有最终决定权；不能声称设置为 4 就保证所有设备无条件全屏。

## 一、入口、取消与状态反馈

- 先追踪当前 `ProfileActivity`、`ChatActivity` 的屏蔽入口、确认弹窗、状态刷新和 Bulletin/Toast 等实际实现，以这些组件和交互为范式。
- 在联系人资料页与聊天页中已有屏蔽操作的位置附近，提供“设为特别关心 / 取消特别关心”。菜单随真实状态切换，进入页面或重启后正确恢复。适当显示不挤占姓名的特别关心标识，使用原主题和无障碍描述。
- 只允许当前账号已有的真实联系人设置；自己、机器人、群、频道、已删除用户和非联系人不提供可成功操作的入口。未知/失效目标返回明确失败。
- 启用、取消均使用原生组件给予操作反馈。这里“参考屏蔽的通知”指设置动作后的 UI 反馈，不向对方发送消息，不产生假的聊天服务消息，也不让对方获知此私有设置。
- 操作期间防止重复提交；只有后端确认后才更新共享状态与 UI。失败保留旧状态并显示可理解的错误；处理页面销毁、退出、切号及同一槽位重新登录后的迟到结果。
- 增加“特别关心”管理列表，复用原屏蔽用户列表的布局和增删交互，在联系人或通知设置的合理位置进入，便于集中查看和取消。不要把特别关心联系人实际塞进黑名单数据或复用黑名单协议语义。
- 删除联系人、屏蔽联系人时清除其特别关心状态，解除屏蔽或重新添加不自动恢复；后端和客户端保持一致。已有屏蔽与隐私限制优先，特别关心不赋予联系、发现或通话权限。

## 二、状态持久化与协议

- 特别关心是“账号 A 对联系人 B”的单向私有偏好，不能写成 B 的全局用户属性。按稳定 UUID/TL 身份关联，不按姓名、Gram ID 或手机号字符串关联；修改 Gram ID 不丢失关系。
- 后端提供查询列表、设置、取消及客户端恢复所需的明确契约。优先扩展现有版本化 typed Protobuf RPC 和现有联系人模型，客户端原页面继续消费原模型与控制器。不要仅做内存或单设备开关，不引入自动 TL JSON 回退。
- 查询、写入均验证 Bearer、本人归属与联系人资格，设置/取消幂等且持久化成功后才返回成功。LegacyOnly 文件存储与 PostgreSQL 路径行为一致，兼容旧数据缺省为 false。
- 多设备登录时通过已有事件提示/差分或明确的 revision 同步机制刷新该私有偏好；不要把自定义偏好版本当作消息 pts，也不要随意修改原 TL 二进制格式。
- 客户端建立按账号及认证会话隔离的本地持久化缓存，使后台来电可立即判定。网络查询不能阻塞通知发布和响铃；状态未知按普通 3 级处理，后台补同步。退出后清理对应缓存，不继承同一槽位旧账号的设置。
- 设置成功、启动恢复、重连和其他设备变更后更新控制器、管理列表与原页面。并发设置/取消不能因乱序回包或旧查询覆盖新状态。
- 如需 PostgreSQL schema 变更，按仓库现有离线迁移机制完成迁移与回滚验证；不在启动时擅自迁移，不操作正式库。

## 三、类似 QQ 的特别关心消息提醒

- 特别关心联系人的一对一新消息使用可辨识的专属提示音、震动与“特别关心”标识，保留原发送者、消息预览、回复、已读及点击跳转能力。提供独立通知频道和原设置体系中的声音/震动配置入口；默认音效使用项目已有可合法复用的资源或原创资源，不下载、复制 QQ 专有音频。
- 使用原 `NotificationsController` 及现有推送/差分处理链路实现，覆盖前台应用内提醒和后台系统提醒；不能只在打开聊天页时起作用。仍受当前后台连接、系统回收和深度休眠能力边界约束。
- 不因特别关心重复发送同一条通知、重复播放音效，或把差分历史重放当作新消息。多账号并存时使用消息所属账号判定，不能只读 `UserConfig.selectedAccount`。
- 尊重用户显式设置的会话静音、全局通知开关、提示音开关及系统频道设置。特别关心默认不绕过免打扰，不自动申请或强行修改 DND 权限；如用户已在系统中调整频道，保留其选择。
- 普通消息通知保持原行为。群聊中出现特别关心联系人发言、提及或转发，不自动提升整个群的提醒；本轮特别关心增强提醒限一对一新消息。
- 未接来电继续沿用当前独立未接通知的去重、隐私和点击跳转逻辑，不把历史未接来电改成全屏响铃通知。

## 四、来电频道与后台全屏策略

当前排查起点（实施前重新核实）：

- `messenger/voip/IncomingCallNotificationChannel.java` 为所有来电选择同一个稳定高优先级频道，并可能复用旧 `incoming_calls4*` 频道。
- `VoIPPreNotificationService.java`、`VoIPService.java`、`VoIPGroupNotification.java` 都调用该 helper，且存在 `setFullScreenIntent(...)`。
- 已有前后台来电、稳定通知频道、局域网 WS 和未接通知功能必须保留。

实现要求：

1. 统一封装按账号、实际来电人及呼叫类型计算通知策略的入口。pre-notification、服务接管、通知更新与重复投递使用相同策略，避免先发 4 级再降为 3 级造成瞬间抢屏。
2. 普通和特别关心使用不同的稳定频道 ID，初始重要性分别为 3 和 4。已存在频道重要性不能靠重复 `createNotificationChannel` 修改；不要每次来电删除重建频道、递增 ID 或绕过用户手工降低的重要性。迁移时普通来电不得继续选中历史高优先级频道；新频道策略清晰且迁移只执行一次，历史共享频道不直接继承为所有特别关心的强制 DND 设置。
3. 旧 Android 版本设置与上述语义对应的 builder priority，普通来电同样不附带 full-screen intent。
4. 全面审计 `startActivity`、PendingIntent、锁屏/唤醒、ConnectionService/Telecom 和服务接管路径。不能仅去掉一个 `setFullScreenIntent`，却仍从其他后台回调为普通来电自动拉起通话页。
5. 特别关心一对一来电保留原来可用的后台全屏能力和原 `VoIP` 页面，正确处理 Android 版本差异与全屏意图权限；权限不足时降为正常可接听通知，不崩溃、不反复跳设置。不要绕过系统限制强行启动。
6. 普通来电保留接听、拒接、铃声、震动、超时及服务存活能力，改变的重点是默认 3 级与不在后台自动全屏。用户主动点击接听或通知后允许正常打开通话页，不能被策略拦截。
7. 本轮群通话邀请按普通 3 级处理，不因邀请者属于特别关心就升级整个群来电。不影响已接通通话的 ongoing 前台服务通知，不降低通话媒体或保活能力。
8. 设置变化影响后续来电；当前正在响铃的同一个 call 不因取消/启用或服务接管而重复全屏、重复响铃。按 call identity 固定本次策略并在终态清理，重启恢复安全降级。
