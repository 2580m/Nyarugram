客户端为当前 `Botgram` 仓库，后端为同级 `../Botgram.Backend`。开始前阅读两仓库 `AGENTS.md`、客户端 `Docs/Botgram.Android.md`、`Docs/Botgram.GID.md`、`Docs/Botgram.Chinese.md`、`Docs/Botgram-E2EE.md` 和 `Docs/artifacts/e2ee-delivery.md`。涉及服务运行时阅读后端 `DEPLOYMENT.md`。以当前源码为准，保留已有用户修改，行号只作定位，不以历史产物或报告代替本轮证据。

## 一、范围与不变量

- 保留原个人主页、聊天页、会话列表、密码锁和隐私设置；保留账号级四位数字 PIN、联系人与非联系人入口及加密聊天管理列表。
- 继续使用真实 libsignal 协议，不自行替换为模拟加密或自创消息加密协议。PIN 只保护本机密钥，不能作为消息密钥。
- 普通未开启 E2EE 的聊天、群聊、收藏夹、原生未绑定账号和原应用密码锁必须保持原有行为；绑定但过期的账号仍不得回落原生网络。
- 项目由用户自行部署，不加入公共服务器或托管密钥服务。不要新增公网服务地址。
- 本任务包含隔离测试与发布物准备，不自动授权升级或重启既有服务、开放端口、修改正式数据库、删除真实用户密钥或恢复正式快照。
- 全部新依赖、工具及缓存放 `D:\BotgramBuild`，固定版本与校验值；不反复下载现有环境，不递归清理依赖 junction。

## 二、逐项修复

### 1. Android Keystore 不接受当前加密 IV 用法（P1）

定位：`BotgramE2eeController.deviceCipher()` 和 `key()`。

现状：创建 Keystore AES 密钥时保留默认 `randomizedEncryptionRequired=true`，加密时却自行生成 IV 并传入 `GCMParameterSpec`。Android Keystore 会拒绝 caller-provided IV；当前宿主 `FixedDevice` 使用普通 AES，不会暴露此问题。

要求：

- 加密时让 Android Keystore 生成 IV，随后读取并保存 `cipher.getIV()`；解密时使用保存的 IV。
- 不以关闭随机化要求、改成可导出软件密钥或绕过 Keystore 作为修复。
- 验证真实 Android Keystore 下的创建、解锁、改 PIN、重启与设备密钥失效。无设备时保留可运行的设备验证入口，并明确未执行，不能把普通 JCE 替身测试称为 Keystore 实测通过。

### 2. PIN 与设备封装是两条独立解密路径（P1）

定位：`BotgramE2eeVaultFile.create/open/changePin/rewrapPin`。

现状：`pinBlob` 与 `deviceBlob` 分别封装同一把 `vaultKey`。读取文件后，只要知道 PIN 就能绕过设备解密；能够使用设备密钥时也能绕过 PIN。四位 PIN 可以在复制出的文件上离线穷举，不受应用重试退避限制。

补充探针已经对合成数据确认：`VAULT_DECRYPT_WITHOUT_DEVICE=true`、`VAULT_DECRYPT_WITHOUT_PIN=true`。

要求：

- 改为 PIN 和设备密钥必须共同参与的保护结构，例如把 PIN 封装结果整体置于 Keystore 外层封装之内；不得在文件中保留任一可单独恢复 vaultKey 的旁路。
- 明确文件复制、仅知 PIN、仅能读取持久化数据、能调用本机 Keystore、设备完全失陷等威胁边界。不宣称四位 PIN 能抵御完全失陷设备上的所有猜测或内存攻击。
- 通过负向测试证明：仅持有文件和正确 PIN、但无对应设备密钥时不能解密；合法应用解锁路径必须同时验证 PIN 与设备层。
- 改 PIN 只重封装保护层，不替换身份、棘轮或聊天关系。失败不得覆盖或删除唯一可读的 vault。

### 3. 普通文字发送被 E2EE 拦截错误阻断（P1）

定位：`SendMessagesHelper.sendMessage()` 中调用 `encryptForSend()` 的代码，以及 `BotgramE2eeController.refreshStatus()`。

现状：非 Secret Chat 的普通文字无条件进入 E2EE 发送检查，没有限定绑定账号和支持的私聊范围；未开启会话的状态查询只将 peer 加入 `known`，没有把构造的 disabled 状态保存到 `statuses`，之后 `encryptForSend()` 仍得到空状态并抛出 `E2EE_STATUS_UNKNOWN`。

要求：

- 仅在适用的 Botgram 普通用户私聊中执行 E2EE 检查，不拦截未绑定原生账号、群聊、频道、收藏夹及其他不适用对象的正常发送。
- 成功确认未开启时保存完整 disabled 状态；状态未知、请求失败与已知关闭必须区分。请求失败不能推断为 disabled，也不能允许已加密聊天以明文发送。
- 处理状态刷新与发送并发、旧响应覆盖新状态、关闭后重开和账号切换；不能只用一个永久 `known` 标记绕过安全检查。
- 回归至少包含：从未开启的联系人/非联系人、关闭后的会话、群文字、收藏夹、未绑定原生账号、未知状态失败、活动加密聊天拒绝明文。

### 4. 后台/切号后迟到解锁可重新安装密钥（P1）

定位：`BotgramE2eeController.createPin/unlock/install/lock/resetLocalVault` 及相关回调。

现状：PIN 派生与文件读取在后台完成后直接 `install()`，未检查前后台、绑定身份或锁定代际。派生期间发生后台锁定、切账号或退出时，先执行的 `lock()` 不能阻止迟到任务重新解锁。部分任务还会重新读取当前身份构造路径，存在跨会话写入风险。

要求：

- 操作开始捕获稳定的服务器/账号/会话身份、目标路径、vault 实例及代际；执行结果安装前再次检查。
- 锁定、切号、退出、重置和会话替换使旧操作失效；废弃结果不得安装密钥、修改新账号文件、清除新账号退避或触发旧 UI 成功导航。
- 废弃任务妥善清理临时密钥材料。页面销毁、取消后的回调也要处理。
- PIN 重试检查在实际执行时也受串行化与限速约束，不能提前排队大量请求后绕过之后产生的退避。
- 使用可控屏障验证“开始派生 → 后台/切号/退出/重置 → 任务完成”各顺序，最后必须仍锁定且账号隔离。

### 5. 棘轮状态与发送/接收结果没有可靠提交边界（P1）

定位：`BotgramE2eeVault.setDirty()`、controller 的 `persistVault/persistDisplay/lock/encryptForSend/decryptForDisplay`。

现状：状态改变只异步排队保存，消息密文已经返回供发送；锁定会清空后台保存任务需要读取的当前状态，任务可能直接跳过。进程崩溃或磁盘失败也可能导致密文已投递而棘轮仍停在旧状态。接收端的已消费密钥状态与可重读历史分别写入，同样存在不一致窗口。

要求：

- 定义并实现可靠提交协议：新的棘轮状态和待发送信封必须持久化成功后才允许网络发送，重试使用相同幂等标识和原信封，不重新消耗棘轮或复用已使用密钥。
- 接收端只有在验证成功、协议状态和可重读的加密历史可靠提交后，才将其视为接收成功；崩溃后能幂等重放或恢复。
- 不依赖“worker 通常会及时跑完”。锁定不能丢弃待提交状态，也不能因此让后台保留可用解锁会话；采用明确快照、串行事务或适当日志机制，处理账号代际和失败传播。
- 写入失败应阻止成功反馈，不只记录日志后继续。原子替换失败不得先删除唯一有效文件。
- 增加磁盘失败、提交前后进程终止、锁定与保存交错、网络成功但回执丢失等故障注入回归，验证密钥不复用、消息不重复、状态不倒退。

### 6. 身份替换确认被已有 session 的提前返回绕过（P1）

定位：`BotgramE2eeController.prepareSession()` 的 `state.hasSession()` 分支，以及 `trustNextPrepare` 和身份确认流程。

现状：已有 session 就直接返回，早于后续替换信任及删除旧 session 的逻辑。对端重装、更换身份后，双方确认仍可能继续使用旧 session。

要求：

- 复用会话前检查经过确认的对端身份、设备 generation、协议及必要 epoch，不能仅按 UUID/deviceId 判断存在。
- 身份替换必须显式确认，绑定确认时展示的确切身份/generation；等待期间再次替换身份时，旧确认不得自动信任后来的新密钥。
- 确认后作废受影响旧会话，可靠建立并提交新会话；失败不显示为可安全发送。安全码必须反映实际使用并信任的身份，不只显示服务端刚返回的公钥。
- 使用 controller 的实际决策流程验证“旧 session 已存在 → 对端换身份 → 暂停 → 双方确认 → 新会话收发”，不能只调用底层 `prepareSession(..., true)` 证明 controller 已修好。

### 7. 内层上下文验证失败仍消耗棘轮状态（P1）

定位：`BotgramE2eeCrypto.decrypt()`。

现状：libsignal 解密先修改 vault，然后才检查内层与外层上下文。不合法的外层会话等字段导致拒绝时，棘轮与预密钥状态已经变化。

补充探针顺序：创建尚未消费的合法信封，修改外层 conversation 后首次提交，得到上下文错误；vault 序列化前后不同；再提交未修改原信封，得到 `DuplicateMessageException`。当前旧回归先消费消息再修改上下文，可能只测到重放拒绝而未覆盖本缺陷。

要求：

- 在可回滚/隔离的协议存储事务或候选状态上解密和验证，全部验证成功后才提交变更；失败不消费预密钥、更新信任或推进棘轮。不要调用有副作用的 decrypt 后仅抛异常。
- 除内外字段相等，还要绑定本机设备、实际目标聊天、对端身份、协议和允许的历史 epoch 上下文，不能让内外同时被替换或跨聊天搬运的信封通过。
- 先验证所有无需解密的格式、大小、消息类型和路由字段，失败没有状态副作用。
- 回归按上述“无效首次投递 → 合法原消息成功 → 合法重复被拒绝”的顺序执行，并比较失败前后的协议存储与持久化结果。

### 8. 5000 条显示缓存是旧历史的唯一可读副本（P2）

定位：`BotgramE2eeDisplayCache` 与 `decryptForDisplay()`。

现状：缓存最多 5000 条，淘汰后接收消息的旧密钥已被消费，自发消息也没有接收端 session 可再次解密。用户 PIN 正确、设备密钥完好时，正常浏览超限仍会永久失去旧历史显示能力。这不只是可接受的缓存命中率问题。

要求：

- 区分有界内存显示缓存与持久化加密消息历史。历史使用本机受保护的高强度密钥认证加密，按账号、聊天和稳定消息身份绑定，支持分页重载。
- 内存淘汰不能删除唯一可读副本；锁定、重启、关闭后重新开启仍能读取此前已成功保存的历史。忘记 PIN 或设备密钥失效后的不可恢复边界保持清楚。
- 本机历史密文与协议状态按第 5 项可靠提交；不得把解密文本写回原 SQLite 明文列、引用、草稿、索引、日志或通知。
- 回归至少超过 5000 条并触发淘汰，重启、解锁、分页读取首批及末批，覆盖自己发送和收到的消息；说明修复前已经丢失的历史无法凭空恢复。

### 9. 自写派生函数不符合 PBKDF2 标准（P2）

定位：`BotgramE2eeVaultFile.derive()`。

现状：首轮为 `HMAC(PIN, salt)`，缺少 PBKDF2 的大端块编号；与 JCE `PBKDF2WithHmacSHA256` 相同参数结果不一致。不能继续在文档中称其为标准 PBKDF2。

要求：

- 优先使用适配支持 Android API 的标准实现，确需兼容路径时使用受验证的实现，不自行创造 KDF。
- 使用标准已知向量和独立实现交叉验证，覆盖随机盐、前导零 PIN、参数边界和真实文件读写。
- 结合第 2 项升级 vault 文件版本，明确 KDF、盐、参数、封装层及 AAD 的格式和限制。不能原地改函数后让所有旧 PIN 都无法打开。
- 旧格式只能在正确 PIN 和对应设备密钥验证后迁移，迁移保持身份、公钥、session 与历史不变。原子写入失败保留可读旧副本；读取旧格式用于迁移不代表继续将脆弱格式作为正常长期存储。
- 迁移前已有文件副本的弱保护不能通过升级追溯消除，文档必须说明；不得自动销毁旧密钥或悄悄建立新身份冒充迁移成功。

8. 所有源码结束后再构建，编译期间不继续修改源码。设备可用时执行真实 Keystore、双机握手/收发、身份替换、后台锁定、切号和重启历史验收；设备不可用时明确未执行，不能填写通过。
