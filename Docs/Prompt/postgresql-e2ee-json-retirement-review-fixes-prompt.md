## 问题一，身份确认未绑定用户实际看到的身份

### 复核证据

- `PostgresBackend.E2ee.cs` 的 `E2EeConfirmIdentity` 分支读取当前设备 generation，并与服务端会话记录比较。
- `Protocol/botgram_rpc.proto` 的 `E2eeActionRequest` 只有 peer、action、protocol_version，没有用户当时看到的身份信息。
- Android `BotgramE2eeController.action` 仅在本地捕获身份，并在收到响应后检查。此时服务端可能已经提交确认。
- 隔离实测先构造旧确认请求，再让对端替换身份。另一方推进确认状态后，旧请求仍能把会话激活为 `ACTIVE`，响应中的 peer generation 已变为 3。

### 修复要求

- 身份确认请求携带用户实际确认的精确公钥与 generation，并按需要绑定会话 epoch 或独立的身份变更版本。
- 服务端在同一事务和适当锁保护下，比较请求快照、当前设备身份及会话状态。任何不匹配都应明确拒绝，失败不增加确认人、不激活会话、不推进 epoch、不产生服务消息。
- 双方确认分别绑定其实际观察到的身份。以明确的双方身份版本表示确认上下文，避免使用 generation 求和代替身份绑定。
- 缺少必要确认字段的旧请求明确失败。禁止默认填充当前身份使其获得确认权限。
- 更新协议、生成代码、Android 请求构造、错误处理和必要的存储迁移。复用原安全码和身份变更 UI。
- 检查旧存储路径的同类确认逻辑，使保留路径也遵守该确认约定。

### 验收

- 用户确认旧身份期间，对端再次更换身份，迟到请求必须失败。
- 另一方先操作、双方并发替换、请求重放、服务重启后，旧确认仍不能确认新身份。
- 对当前身份的正常双方确认可以完成，失败请求无状态和事件副作用。

## 问题二，合法负数 random_id 被拒绝

### 复核证据

- `PostgresBackend.E2ee.cs` 使用 `long.TryParse(..., NumberStyles.None, ...)` 解析 `tl:` 后的随机 ID，该样式拒绝负号。
- Android `SendMessagesHelper.getNextRandomId()` 使用非零随机 `long`，负值属于正常输入。
- 隔离实测 `random_id=-7100000000001` 的合法单方密文返回 HTTP 400。

### 修复要求

- 按协议支持完整的有符号 64 位随机 ID，保留现有零值限制和合法格式约束。
- 确保请求字段、幂等键、信封、数据库与响应映射一致，避免转成绝对值、截断或使用 JavaScript Number 丢失精度。
- 校验字串格式时保持严格，正确拒绝溢出、空值和其他非法输入。

### 验收

- 覆盖正数、负数、`long.MinValue`、`long.MaxValue` 及非法输入。
- 分别测试单方类型 4、双方类型 2/3，以及同一随机 ID 的重试和冲突。
- 使用客户端真实的随机 ID 生成及 Protobuf 映射路径验证。

## 问题三，状态变化使已提交消息失去幂等重试能力

### 复核证据

- `PostgresBackend.Rpc.cs` 的发送分支先调用 `ValidateSend`，随后才进入 `PostgresMessageAcceptance` 的已有消息查重逻辑。
- 隔离实测单方密文首次发送返回 200，对端开启使会话激活后，原随机 ID 和原信封重试返回 409。
- 首次提交响应丢失时，客户端因此无法通过重试确认原消息的提交结果。

### 修复要求

- 在保留认证、成员权限和数据隔离检查的前提下，优先识别已提交的同一发送者、会话及幂等键。
- 匹配已提交记录后完整比较内容、规范信封、回复、实体和其他发送选项。一致请求返回原消息及正确的现有响应语义，不一致请求返回明确冲突。
- 只有新发送才按当前 E2EE 状态、方向、epoch 和身份执行准入校验。
- 查重、状态检查与提交保持并发一致性。新消息不能借重试路径绕过当前加密要求或成员权限。

### 验收

- 首次提交后模拟响应丢失，随后分别接受加密、关闭、重开、身份替换、重启，再重试原消息。
- 原请求始终返回同一消息 ID，消息、pts、事件、Outbox 计数不重复推进。
- 相同键携带不同内容仍冲突，已撤销会话或无权限账号仍被拒绝。
- 检查普通明文消息在随后启用加密后的同类重试。

## 问题四，PostgreSQL 单独运行模式的 Outbox 没有完成处理链路

### 复核证据

- 交付报告声明本次正式运行选择 `RelationalBackend`，未启动 Kafka、Scylla、Redis 及四组件工作进程。
- `PostgresMessageAcceptance.CapacityCountSql` 统计未发布、未消费或未完成投影的 Outbox，默认限制为 100,000。
- 消息和通用事件都使用该限制。现有 `RelationalMaintenanceService` 仅维护通话和会话过期，没有处理该模式下的 Outbox 完成状态。
- 在持续写入下积压会增长，最终使消息和相关业务持续返回 `storage_backlog_full`。

### 修复要求

- 明确 `RelationalBackend` 与 `FourComponent` 的交付职责，为正式启用模式提供完整的 Outbox 生命周期和容量策略。
- PostgreSQL 单独运行时，按真实处理职责设计事件保留、完成条件、清理、监控及重启恢复。若启用四组件，完成对应真实服务部署、工作进程和故障恢复验证。
- 必须保持消息、事件及未来切换所需数据的可靠性。禁止仅调大阈值、关闭容量检查或批量伪造 Published/consumed 来消除报错。
- 对已有积压给出兼容升级与恢复办法，保证升级重复执行及中断后的状态一致。

### 验收

- 使用小阈值执行可重复的容量回归，连续处理超过阈值数量的消息及通用事件，验证健康运行时积压能按设计完成或释放。
- 模拟处理停机，验证真实积压达到限制时明确拒绝，再恢复处理并验证写入恢复。
- 验证重启、重放、并发写入、读历史与差分同步的完整性。
- 四组件模式保留原有持久投递、消费、投影完成和背压语义。
