# PostgreSQL 端到端加密接入与 JSON 接口弃用

你需要在现有 Botgram 项目中完成下面两项工作，并把匹配的客户端、后端及正式部署交付到可验证状态。

1. 补齐 PostgreSQL 后端的 E2EE 功能，解决相关接口返回 501 的缺口，将正式业务接入已有 PostgreSQL 存储实现。
2. 将全部 JSON 通信接口标记为已弃用，任何请求都明确返回错误，客户端业务通信统一使用 Protobuf。

先核对源码和运行状态，然后执行修改、测试和交付。仅完成调查、文档、关闭开关或返回错误不满足本任务。

## 用户明确约束

- 保留 `botgram.json` 文件存储代码及已有文件。用户已明确撤回删除这部分代码的要求。
- 正式业务使用 PostgreSQL。保留旧存储代码不能成为继续部署 `LegacyOnly` 的理由。
- PostgreSQL 的账号、联系人、会话、消息、同步、隐私和通话等大量接口已经有实现，沿用这些实现补齐缺口。
- JSON 接口弃用与 PostgreSQL 数据持久化分别处理。HTTP/WS 编码、JSON 文件存储、PostgreSQL 中现有 JSONB 字段各自独立。
- PostgreSQL 的现有 JSONB 业务字段、配置文件、离线导入工具及备份可继续使用。不要因“禁用 JSON 接口”删除它们。
- 现有账号、密码摘要、有效会话、UUID、Gram ID、TL 身份、成员关系、消息、回执、游标、隐私状态、验证器密钥及 E2EE 状态必须保留。
- 项目要求用户自部署。公开源码和文档中的地址示例使用私网地址，不写实际公网入口、真实凭据或连接字符串。

## 第一项工作，补齐 PostgreSQL E2EE 并接入正式业务

### 保留当前产品语义

- 一方开启后立即对该方之后发出的消息生效。另一方收到这些消息时显示“此信息开启了端到端加密”，聊天中显示原生居中服务消息“对方开启了端到端加密”。
- 未开启的一方仍可向已开启的一方发送普通消息。
- 单方阶段的消息没有接收方密钥，旧消息永久保持占位。双方后来都开启时，只有新消息可读，禁止设计追溯恢复旧消息的机制。
- 双方开启后的新消息继续使用现有 libsignal 协议。保留操作语义版本 2、信封版本 1，以及单方类型 4、双方类型 2/3 的实际协议约定。
- 关闭只影响本人之后发出的消息，保留另一方的开启状态。
- 保留账号级四位 PIN、既有安全封装、锁定、身份确认、历史恢复和失败提交保护。服务端只处理公开密钥、协议状态和密文。

### PostgreSQL 实现要求

1. 在已有关系化后端接入设备发布、预密钥目录、一次性预密钥消费、会话操作、单个/批量状态、加密聊天列表、对端 bundle、密文发送、历史和差分同步。
2. 按实际需要增加版本化 schema 迁移。保留已有表和数据，支持新库初始化、既有 schema 升级及重复执行。明确验证 schema 兼容边界。
3. 预密钥并发消费、设备 generation、身份替换、会话状态和 epoch 的变化必须有事务及并发保护。
4. 在同一可靠提交边界处理消息、幂等键、稳定消息 ID、会话序号、pts、事件、Outbox 和相关状态。重复请求复用原结果，相同幂等键携带不同内容必须冲突。
5. 正确校验成员身份、方向、设备、epoch、信封大小和类型。加密方向拒绝明文，允许的反向普通消息保持正常。非法或失败请求不能消费预密钥或提交部分状态。
6. 保留身份替换后的暂停及明确确认行为，迟到确认不能确认后续替换的新身份。
7. 原生服务消息通过现有消息和同步链路投递，正确保持排序、历史边界和重放行为。
8. 核对 PostgreSQL 权威存储以及既有 Kafka、Scylla、Redis 链路的信封、服务消息和状态兼容性。禁止在投影或缓存中写入加密消息明文。
9. 复用已有校验和协议逻辑，保持其行为。禁止把整个旧数据库快照塞进 PostgreSQL 来替代已有关联表实现。
10. 完成后，正常 PostgreSQL E2EE 操作应真实执行。仅删除 501、伪造成功、返回空数据或暗中回落 JSON 文件均不满足验收。

### 正式存储接入

- 根据已有关系化和四组件实现补齐生产配置、启动校验、连接及工作进程管理。验证环境继续保留其隔离限制。
- 禁止把正式环境伪装成 Development 或将正式库改成测试库命名来绕过限制。
- 使用用户已经选择的新存储结构，核对现有四组件权威、投影、缓存和工作进程职责。任何必要的范围调整都需在交付记录写清实际结果。
- 正式启动必须明确选择新存储模式。连接失败、schema 不兼容或必需组件异常时给出明确错误，禁止自动切回 `LegacyOnly`。
- 先定位真实目标数据、配置、密钥环及已有迁移结果，再决定导入步骤。目标库已含真实数据时，禁止覆盖、清空或将旧 JSON 直接灌入。
- 复用并扩展现有离线迁移工具，覆盖 E2EE 新数据。迁移保持 UUID、Gram ID、TL ID、令牌摘要、有效会话、消息和同步游标稳定。
- 停止相关写入者后取得一致备份，验证迁移指纹及关键不变量，保留旧文件、旧镜像和配置。迁移中断、重复执行及恢复路径都必须有明确行为。

## 第二项工作，全面弃用 JSON 接口

### 弃用范围与响应

- 枚举两种存储路径中的所有 HTTP 路由、WebSocket 子协议及客户端调用方。建立旧入口与 Protobuf 替代入口的清单。
- 范围包括旧 TL JSON RPC、JSON WebSocket、JSON 登录/注册/密码验证，以及其余返回或接收 JSON 的业务 REST 接口。
- 在统一入口拒绝旧 JSON API，请求无需通过身份认证也能得到一致弃用错误。覆盖各 HTTP 方法、尾斜杠及框架支持的等价路径形式。
- 推荐固定 HTTP `410 Gone`，错误码 `BOTGRAM_JSON_API_RETIRED`，添加弃用标记。响应使用明确的非 JSON 错误格式，并由客户端可靠识别。
- 旧接口携带 Protobuf Content-Type 也应被拒绝。Protobuf 入口携带 JSON 正文时拒绝，禁止自动嗅探并回落 JSON。
- JSON WebSocket 在升级前明确拒绝。既有连接、重连和 JSON 子协议协商均需检查，Protobuf 事件通道继续正常工作。
- 旧开关、账号灰度、存储模式、深链接和其他监听入口都不能重新启用 JSON API。
- 健康检查若仍返回 JSON，改成可供现有健康探针使用的非 JSON 格式，并同步更新探针。协议能力发现同样提供匹配的非 JSON 表示。

### 保证客户端完整可用

- 为仍依赖 JSON 的必要功能提供 Protobuf 替代入口，至少覆盖启动协商、注册、登录、密码及验证器验证、账号恢复所需流程和退出。
- 优先复用已有消息、DTO 语义和协议生成流程。新增协议字段保持稳定编号，明确认证前入口及错误消息格式。
- 同步修改 Android 的实际调用入口、错误处理和协商路径，复用原 Telegram 页面和认证完成流程。
- 检查后台请求、账号切换、重新登录及迟到回调。绑定账号失效时继续隔离原生 Telegram 网络。
- 旧客户端调用旧接口应显示明确错误。新版客户端注册、登录、恢复会话、聊天和 E2EE 必须可以完成。
- 禁止仅关闭登录注册 JSON 入口却不提供匹配客户端，或者保留隐蔽 JSON 登录例外来维持表面可用。
